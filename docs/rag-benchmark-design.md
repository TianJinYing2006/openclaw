# 检索命中率评测与优化决策（RAG 检索质量）

- **日期**: 2026-08-18
- **状态**: 已落地（代码 + 评测 + 简历口径）
- **范围**: 穿搭知识检索（RAGFlow 主链路）的命中率评测、可复现性根治、rerank / query 改写 A/B 决策
- **关联代码**: `ResumeBenchmarkLiveTest`、`QueryAnalyzer`、`AgentLlmCaller`、`RagFlowClient`、`RagFlowProperties`

---

## 1. 问题情景（为什么做这件事）

简历上原本有两个"空心数字"：
1. **"50 条领域语料评测 top-5 命中率 100%"** —— 自建语料、自测自评，指标失真，面试一追问就崩。
2. **"故障窗口内请求成功率 100%"** —— 缺分母、缺验证方法，是空心的。

用户要求：**用真实数据替换空心数字**，并写压测脚本。由此建立了基于真实查询日志的检索命中率评测。

### 1.1 评测集怎么来的（ground truth 自动标注）

- 数据源：`fashion_conversations` 表，取 54 条带 `reference_outfit_id` 的真实用户穿搭查询。
- `reference_outfit_id` = 系统实际采纳的参考穿搭编号，天然就是 ground truth，**无需人工标注**。
- 前提校验：54 个 gt 编号 54/54 都在语料中（排除"文档不在库里"的覆盖干扰）。
- 检索词构造：真实 `QueryAnalyzer`（LLM 分析）+ RAGFlow 主链路检索，与线上链路一致。

### 1.2 评测暴露的核心问题：数字不可复现

同一套配置，不同天跑出 **top-5 46.3% 和 83.3%**，±37pt 波动。根因是 **QueryAnalyzer 的 LLM 随机性**——检索词由 LLM 分析拼接而成，每次分析略有不同，检索质量就剧烈波动。

> 面试官只要说"那你现场再跑一遍"，结果对不上就是灾难。**数字不可复现，就不该上简历。**

---

## 2. 思考策略（候选方案与取舍）

针对"提升检索命中率 + 消除波动"，按直觉列了三条路，全部用**受控 A/B 实测**验证，而不是拍脑袋。

### 2.1 方案 A：加 rerank（语义精排）

- **思路**：RAGFlow 检索接口支持 `rerank_id`，对候选池做交叉编码器精排，理论上能救"gt 在候选池但不在 top-5"的排序问题。
- **实现**：RAGFlow 配置 DashScope `qwen3-rerank`；`RagFlowClient` 支持传 `rerank_id`；rerank 分数量纲与向量相似度不同（实测多在 0~0.2），阈值单独配置（默认 0）。
- **实测（同 run 内、同一份分析、54 条查询）**：

  | 组合 | top-1 | top-5 |
  |---|---|---|
  | 混合检索（baseline） | 14.8% | **83.3%** |
  | 混合检索 + qwen3-rerank | 14.8% | **66.7%** |

  top-5 净回退 9 条（13 回退 vs 4 提升）。原始用户查询 + rerank 也只是 +2（噪声级）。
- **为什么不采用**：交叉编码器对这套结构化 Markdown 穿搭语料区分度差（`144、043、233、004` 等编号反复出现在不同查询的 rerank top-5），且复合检索词里的 `场景:/风格:/季节:` 标签格式会干扰它。**负收益，关闭**（代码保留、配置门控默认关，成本为零）。

### 2.2 方案 B：query 改写（4 变体）

- **思路**：检索词由 LLM 拼接，`场景/季节` 是英文枚举（WORKPLACE/SUMMER），拼进中文语义检索看似低效；prompt 专门生成的 `decomposedQueries`（中英混合检索词）之前根本没被使用。两个直觉假设。
- **实测（同 run 内、同一份分析、54 条查询，排除 LLM 波动干扰）**：

  | 改写方案 | top-1 | top-5 |
  |---|---|---|
  | V1 现状（英文枚举标签） | 11.1% | **83.3%** |
  | V2 枚举→中文关键词 | 11.1% | 81.5% |
  | V3 decomposedQueries 拼接 | 14.8% | 57.4% |
  | V4 多路检索合并（V1+V3+原始） | 11.1% | 75.9% |

- **为什么不采用**：两个直觉假设都被数据否定——V1 现状就是最优，V3 用 decomposedQueries 反而暴跌 26pt（这类语料不适合把它拼成单句检索词）。**零无效改动**。

### 2.3 方案 C：根治方差（贪婪采样 + 缓存）—— 最终采用

- **思路**：既然波动来自 QueryAnalyzer 的 LLM 随机性，就从源头消除——**贪婪采样（temperature=0）** 让同一输入每次输出确定；再加 **Caffeine 同 query 分析缓存**（30min）保证评测/线上多次调用结果一致。
- **实现**：
  - `AgentLlmCaller` 新增 `callAgentGreedy`（temperature=0），只给 QueryAnalyzer 用，不影响 Stylist/Critic 等其他 Agent 的多样性。
  - `QueryAnalyzer` 改贪婪采样 + Caffeine 缓存；新增 `analyzeUncached` 供评测绕过缓存（否则三轮必然相同、无法验证确定性）。
- **实测（3 轮重测，每轮独立真实 LLM 分析）**：

  | 轮次 | top-1 | top-5 |
  |---|---|---|
  | 第 1 轮 | 11.1% | 85.2% |
  | 第 2 轮 | 14.8% | 85.2% |
  | 第 3 轮 | 16.7% | 85.2% |

  **top-5 稳定在 85.2%（46/46/46，0 波动）**，top-1 波动收窄到 11.1%~16.7%。简历数字从此可复现。
- **为什么采用**：A/B 证明 rerank 和 query 改写都无正收益，而波动是"数字能不能上简历"的硬门槛。贪婪采样 + 缓存直接根治波动，且改动小、不影响其他 Agent、不改变检索词构造（V1 现状已被证明最优）。

---

## 3. 最终决策与简历口径

- **检索词构造不变**（V1 现状，A/B 证明最优）。
- **rerank 关闭**（配置门控默认关，负收益）。
- **QueryAnalyzer 贪婪采样 + 缓存**（根治波动）。
- **简历主数字**：top-5 **85.2%（46/54，3 轮 median，0 波动）**；top-1 median 14.8%。MySQL FTS 兜底对照 top-5 仅 3.7%。
- **面试叙事**：真实数据 + 自动标注比自建语料严格得多 → 贪婪采样保证可复现 → rerank/改写双 A/B 负收益 → 零无效改动 → 回归评测固化。

## 4. 回归评测（固化）

`ResumeBenchmarkLiveTest` 新增三个测试（`RESUME_BENCH_LIVE=true` + `RESUME_BENCH_RAG_PROVIDER=ragflow` 才运行，不影响日常构建）：

| 测试 | 验证内容 |
|------|----------|
| `rerankHitRateComparison` | rerank 前后命中率对比（baseline vs qwen3-rerank） |
| `queryRewriteComparison` | 4 种 query 改写方案对比（V1~V4） |
| `greedyStabilityRerun` | 贪婪采样 3 轮重测，验证数字可复现 |

每次改动检索链路，跑一遍回归，用数据说话。

---

## 5. 环境注意点

- 评测依赖 RAGFlow（9380 端口）与 Docker Desktop。**Docker Desktop 未启动时 RAGFlow 连不上，检索返回空 → 命中率假性 0%**。跑评测前先确认 `docker ps` 与 9380 端口可达。
- RAGFlow 侧已配置 `qwen3-rerank` 模型（DashScope），保留在实例中，供未来复测。
