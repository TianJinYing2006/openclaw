# RAG 检索指标口径统一（Canonical）

> 目的：项目文档中并存多组「检索命中率」数字（24.6% / 36.84% / 37.29% / 83.3% / 85.2% / 91.7% / 93.22% 等），
> 面试官会认为口径混乱。本文把这些数字**逐一归位**到「数据集版本 + 样本量 + 指标定义 + 重排配置 + GT 定义」，
> 并给出**当前可引用 / 已废弃**的结论。
>
> 本文只做口径归位，不重新计算数字；每个数字标注来源文档，冲突处明确标注「不可跨版本比较」。

---

## 1. 为什么数字会「打架」

同一句「top-5 命中率」在四种条件下含义不同：

1. **数据集不同**：`fashion_conversations` 的 54 条、P5 结构化输出评测的 59 条、README 的 57 条，是三次不同时间/不同种子的采样。
2. **指标不同**：`strict top-k`（GT 是否落在最终 top-k）与 `候选池召回`（GT 是否在 top-20/top-50 候选里）不是一回事。
3. **重排配置不同**：无重排 / 单路规则重排 / `qwen3-rerank` 交叉编码器，三者结果不可比。
4. **检索词构造不同**：是否启用贪婪采样（temperature=0）+ 缓存，会带来 ±37pt 波动（见 `rag-benchmark-design.md`）。

因此**任何跨版本的百分比比较都是无效的**；只有「同一数据集 + 同一配置」内的前后对比有效。

---

## 2. 指标定义（引用时必须同时声明）

| 术语 | 定义 |
|---|---|
| 数据集 | 哪一批真实查询（54 / 57 / 59 条），来源表 `fashion_conversations` |
| GT | ground truth = 系统实际采纳的参考穿搭编号 `reference_outfit_id`（自动标注，无人工偏差） |
| strict top-k | GT 编号是否出现在**最终返回的 top-k** 里 |
| 候选池召回 Recall@N | GT 编号是否出现在**候选池前 N**（用于判断瓶颈是召回还是排序） |
| 重排 | 无 / 单路规则重排 / RAGFlow `qwen3-rerank` |
| 检索词 | QueryAnalyzer 构造；是否贪婪采样 + 缓存 |
| 兜底对照 | MySQL FULLTEXT（`fashion_seed_fts`）关键词检索 |

## 4. 可引用结论（面试/简历）

- **不要给一个孤立的百分比**。标准说法示例：
  > 「在 **59 条真实用户查询**、GT 为系统实际采纳编号、**单路规则重排**的生产口径下，strict top-5 = **37.29%**；
  > 候选池 Recall@50 = **93.22%**，说明瓶颈在排序而非召回。另一版 **54 条**评测在贪婪采样+缓存后 top-5 = **85.2%**
  > 且 3 轮 0 波动；两版数据集不同，不并列比较。」
- **必须强调**：数字可复现（贪婪采样 + 缓存）比数字高低更重要；rerank 与 query 改写均经 A/B 否决（负收益）。
- **兜底对照**：MySQL FTS 仅 3.7%，是「必须做 RAGFlow」的证据。
