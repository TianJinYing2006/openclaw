# 穿搭垂直 Agent — 业务逻辑梳理

## 一、一句话定位

用户在微信里发一句穿搭需求，系统经过 RAG 检索 → 多 Agent 辩论 → 规则校验 → 偏好学习 → 输出推荐方案。

---

## 二、完整用户故事

### 场景示例

> 用户小美在微信里发：
> "下周要去参加朋友的婚礼，帮我推荐一套穿搭。我身高162，偏梨形身材，喜欢简约风。"

### 系统响应（用户看到的）

```
帮你分析了婚礼场景和你的体型特点，推荐方案如下：

【首选推荐】
米白色真丝衬衫 + 浅粉色收腰A字连衣裙 + 裸色方头低跟凉鞋
配饰：珍珠耳钉 + 米白编织手拿包

理由：
- 米白+浅粉的邻近色搭配，温柔不失正式
- 收腰A字裙优化梨形身材比例
- 方头低跟凉鞋比高跟鞋更适合户外婚礼
- 真丝材质符合夏季透气需求

【备选方案】
雾霾蓝V领雪纺连衣裙 + 银色一字带凉鞋
简约大方，适合不喜欢粉色的用户

【如果天气转凉】
方案一的外面可以加一件米白色亚麻小西装
```

## 三、业务流程图

```
用户发消息
    │
    ▼
┌──────────────────────────────────────────────────────┐
│  第一步：路由判断（FashionAgentService）               │
│                                                      │
│  判断用户的输入是否和穿搭相关？                         │
│  ├─ 是 → 走穿搭 Agent 管道（本流程）                   │
│  └─ 否 → 走通用 Chat Gateway（已有功能）               │
│                                                      │
│  "下周参加朋友婚礼..." → 命中关键词: 婚礼/穿/推荐       │
│  → 进入穿搭管道                                       │
└───────────────────┬──────────────────────────────────┘
                    │
                    ▼
┌──────────────────────────────────────────────────────┐
│  第二步：上下文加载（FashionMemoryService）            │
│                                                      │
│  从 SQLite 加载该用户的历史档案：                       │
│  · 用户身份: {userId, 性别, 年龄, 城市, ...}          │
│  · 体型信息: 梨形身材（可能上次对话留下的）             │
│  · 风格偏好: 简约风（偏好向量）                         │
│  · 历史摘要: "上次推荐约会穿搭，用户选了第二套"          │
│  · 偏好权重: 色彩权重高, 品牌权重低                     │
│                                                      │
│  如果是新用户 → 创建空档案                             │
└───────────────────┬──────────────────────────────────┘
                    │
                    ▼
┌──────────────────────────────────────────────────────┐
│  第三步：RAG 知识检索                                 │
│                                                      │
│  这一步的目的：在 Agent 思考之前把相关知识准备好         │
│                                                      │
│  3a. 查询分解（QueryAnalyzer）                        │
│  "下周参加朋友婚礼穿什么"                             │
│      ↓                                               │
│  {                                                    │
│    decomposedQueries: ["婚礼宾客穿搭","夏季婚礼配色"], │
│    params: {scene: wedding, season: summer,           │
│             formality: 4, gender: female}              │
│  }                                                    │
│                                                      │
│  3b. 规则检索（FashionRuleEngine）                    │
│  从 SQLite 匹配 scene=wedding 的规则:                  │
│  · 硬: 避免纯白、避免全黑                              │
│  · 软: 推荐柔和色系、正式度≥3                          │
│                                                      │
│  3c. 语义检索（FashionRetriever）                     │
│  对每个子查询走 BM25 + 向量检索：                       │
│  · "婚礼宾客穿搭" → 找到 10 条相关博主搭配              │
│  · "夏季婚礼配色" → 找到 8 条配色参考                   │
│                                                      │
│  3d. 重排（Reranker）                                 │
│  Top-30 → 重排 → Top-5                               │
│                                                      │
│  3e. 上下文组装（ContextAssembler）                    │
│  产出结构化的知识包:                                   │
│  {rules: [...], references: [...], params: {...}}     │
└───────────────────┬──────────────────────────────────┘
                    │
                    ▼
┌──────────────────────────────────────────────────────┐
│  第四步：多 Agent 协作推理                             │
│                                                      │
│  【Stylist Agent】创意生成                            │
│  输入: 用户需求 + 用户档案 + RAG知识包                 │
│  思考: "婚礼宾客，梨形身材，简约风，夏季..."            │
│  输出: 3 套穿搭方案（JSON）                            │
│  方案A: 米白衬衫+粉色收腰裙+裸色凉鞋（优雅浪漫）        │
│  方案B: 雾霾蓝雪纺连衣裙+银色凉鞋（简约清新）           │
│  方案C: 浅杏色亚麻套装+白色帆布鞋（休闲随性）           │
│                                                      │
│  ┌────── 并行 ──────┐                                │
│  ▼                   ▼                                │
│  【Critic Agent】    【Trend Agent】                   │
│  评审色彩/体型/场景   验证趋势/季节/时尚度              │
│  输出:               输出:                             │
│  方案A: 4分          方案A: 4分（真丝今夏热门）         │
│  方案B: 3分(不够正式) 方案B: 5分(雾霾蓝是今夏流行色)    │
│  方案C: 3分(太随意)   方案C: 3分(婚礼不太搭)           │
│                                                      │
│  └──────────┬─────────┘                              │
│             ▼                                        │
│  【Coordinator Agent】最终裁决                        │
│  输入: 3 套方案 + 评审意见 + 趋势验证 + 用户档案        │
│  裁决逻辑:                                            │
│  1. 优先体型适配 → 方案A的收腰裙最适合梨形              │
│  2. 场景匹配 → 方案A和B都适合婚礼                      │
│  3. 用户偏好 → 用户喜欢简约风, 方案A/B都符合           │
│  4. 趋势 → 方案B的雾霾蓝趋势分最高                     │
│                                                      │
│  裁决结果: 选择方案A, 精炼后输出                       │
│  理由: "方案A的收腰设计优化梨形身材, 米白+浅粉优雅正式" │
│  精炼: 综合方案B的色彩建议, 配饰调整                   │
└───────────────────┬──────────────────────────────────┘
                    │
                    ▼
┌──────────────────────────────────────────────────────┐
│  第五步：规则后校验 + 领域评分                         │
│                                                      │
│  检查 Coordinator 输出是否违反硬约束：                  │
│  · 没有纯白/全黑 → ✅                                 │
│  · 正式度≥3 → ✅                                     │
│  · 是否符合用户体型规则 → ✅ 收腰裙适配梨形             │
│                                                      │
│  计算领域评分：                                       │
│  Score = w1·色彩 + w2·体型 + w3·场景 + w4·趋势       │
│  = 0.3×4.5 + 0.3×5.0 + 0.2×4.0 + 0.2×4.0           │
│  = 4.45 / 5.0                                        │
│  → 通过                                              │
│                                                      │
│  如果评分低于阈值（如 < 3.0）→ 降级到次优方案            │
└───────────────────┬──────────────────────────────────┘
                    │
                    ▼
┌──────────────────────────────────────────────────────┐
│  第六步：偏好记录 + 记忆归档                           │
│                                                      │
│  构建 Bradley-Terry 偏好数据：                         │
│  · 把"选中的方案A"和"未选的方案C"记为一对              │
│  · 提取特征向量: [4.5, 5.0, 4.0, 4.0]                │
│  · 存入 preference_records 表（等待用户反馈）           │
│                                                      │
│  归档本次会话：                                       │
│  · 写入 session_archives 表                           │
│  · 生成摘要: "用户为婚礼咨询，推荐了优雅浪漫风方案..."   │
│  · 更新 user_profiles.total_sessions + 1              │
└───────────────────┬──────────────────────────────────┘
                    │
                    ▼
┌──────────────────────────────────────────────────────┐
│  第七步：输出格式化 + 微信回复                         │
│                                                      │
│  组装最终回复文本:                                    │
│  "帮你分析了婚礼场景和你的体型特点...                   │
│   【首选推荐】...                                      │
│   【备选方案】...                                      │
│   【细节提醒】..."                                     │
│                                                      │
│  如果 VTON 可用 → 生成试穿效果图一起发送                │
│                                                      │
│  发送到微信                                           │
└──────────────────────────────────────────────────────┘
                    │
                    ▼
              用户看到回复
                    │
                    ▼
┌──────────────────────────────────────────────────────┐
│  第八步：用户反馈（可选，偏好学习闭环）                  │
│                                                      │
│  用户回复: "第一套不错，但想换个鞋子"                   │
│  → 系统识别为"采纳方案A + 修改鞋款"                     │
│  → PreferenceLearner.recordPreference()               │
│  → 更新该用户的偏好权重                                │
│  → 下次推荐时权重会影响 Stylist 和 Coordinator         │
│  → 系统越用越懂用户                                    │
└──────────────────────────────────────────────────────┘
```

## 四、核心业务规则

### 4.1 什么时候走穿搭管道

| 触发条件 | 示例 | 路由方式 |
|---------|------|---------|
| 穿搭关键词 | "穿什么/搭配/推荐衣服" | 关键词匹配 |
| 场景词 + "穿" | "去婚礼穿什么" | QueryAnalyzer 判断 |
| 用户主动要求 | "帮我搭一套" | 关键词匹配 |
| 历史延续 | 上次在聊穿搭，这次接着聊 | 记忆驱动 |

**非穿搭请求**：如果输入是"今天天气怎么样"，不触发管道，走通用 Chat。

### 4.2 新用户 vs 老用户

| 用户类型 | 行为 |
|---------|------|
| 新用户 | 创建空档案 → Stylist 根据通用知识推荐 → 推荐后追问偏好 |
| 老用户 | 加载档案 → 偏好权重影响推荐 → 持续更新 |

### 4.3 Agent 裁决优先级

```
Coordinator 在做最终裁决时，按这个顺序判断：

1. 用户体型适配（最高优先）
   - 梨形 → 优先 A 字裙/阔腿裤方案
   - H型 → 优先收腰/强调腰线方案
   违反 → 直接淘汰

2. 场合适配度
   - 婚礼 → 正式度≥3，不能太随意
   - 运动 → 不能是高跟鞋
   违反 → 直接淘汰

3. 用户风格偏好（来自记忆/偏好学习）
   - 简约风 → 淘汰过于花哨的方案
   - 权重影响但不一票否决

4. 趋势热度（最后参考）
   - 同样适配的情况下选趋势分高的
```

### 4.4 无网络/降级模式

| 场景 | 行为 |
|------|------|
| Trend Agent 搜索不可用 | Trend Agent 只用 LLM 自身知识判断趋势 |
| RAG 检索结果为空 | 跳过 RAG，只走规则 + LLM 自身知识 |
| 所有 LLM 调用都失败 | 返回规则引擎的兜底方案（纯规则驱动） |

## 五、核心差异点（和其他推荐系统的区别）

| 维度 | 本系统 | 传统推荐系统 | 通用 Chatbot |
|------|-------|------------|-------------|
| 输出 | 结构化方案（多套+理由+建议） | 商品列表 | 一段文字 |
| 推理 | 多角色辩论式推理 | 协同过滤/矩阵分解 | 单次 LLM 生成 |
| 纠错 | Critic Agent 主动挑刺 | 无 | 无 |
| 知识来源 | RAG + 规则引擎 + LLM 自身 | 用户行为统计 | LLM 自身 |
| 记忆 | 结构化的三层记忆 | 行为向量 | 对话历史 |
| 反馈闭环 | Bradley-Terry 偏好学习 | CTR 模型更新 | 无 |
| 可解释性 | 每个推荐有完整的搭配理由 | "买了的人也买了" | 单次生成 |

## 六、业务数据流转一览

```
用户输入（自然语言文本）
    │
    ▼
结构化查询参数（QueryParams: scene, season, formality...）
    │
    ▼
知识上下文包（RAGContext: rules + references + params）
    │
    ▼
3 套穿搭方案（StylistOutput: 3 x OutfitSuggestion）
    │
    ▼
评审意见 + 趋势验证（CriticOutput + TrendOutput）
    │
    ▼
精炼方案 + 最终理由（CoordinatorOutput）
    │
    ▼
校验通过的结果（ValidationResult + FashionResult）
    │
    ▼
格式化后的微信消息（String + 可选的图片）
```
